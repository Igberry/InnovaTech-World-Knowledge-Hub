**Goal:** Write two professional documents with clear structure, readable formatting and a documented review round.

## Learning Objectives

By the end of this week, you can:

- Apply paragraph styles and heading levels to create a usable document outline.
- Insert and update a table of contents, links, tables and page numbers.
- Share a document with an appropriate role and use comments or Suggesting mode for review.
- Name a version, respond to feedback and explain what changed.
- Export a document and inspect the final copy for layout and accessibility issues.

## Tools / Accounts Needed This Week

Google Docs in a current desktop browser and the Week 2 fictional content files. A laptop is preferred for long documents. Use a practice account you control; a managed account may limit sharing or collaboration.

## Lessons

### Lesson 1: Structure first, styling second

A useful document is easy to scan, edit and navigate. Before changing font sizes, decide what the reader needs to know and in what order. For the WhatsApp-order SOP, a reader needs the purpose, roles, steps, exceptions and escalation path. A proposal needs a request summary, suggested plan, assumptions, timeline and next step.

Start with a clear title and a short purpose statement. Use paragraph styles such as Title, Subtitle, Heading 1 and Heading 2 to express the document hierarchy. A heading is not just bold text: it gives the document outline and can help screen-reader users navigate. Use Heading 1 for main sections and Heading 2 for subsections. Do not skip levels merely because a smaller size looks better.

Use the outline panel to check whether the structure makes sense without reading every paragraph. If the headings read like a useful summary, the document is probably easier to navigate. If they say only "More information" or "Other", revise them to explain what follows. Keep paragraphs short and put related actions in a list or table.

Direct formatting changes visual appearance but does not reliably communicate structure. Apply a heading style first, then adjust the style if needed. Avoid changing every heading independently; a consistent style makes later edits faster. Use the same date format, currency format and capitalization throughout the document.

### Lesson 2: Lists, tables, links and page layout

Use numbered lists when sequence matters, such as order handling steps. Use bullets for items where order does not matter. Keep list items parallel: begin each with an action or a noun phrase, and avoid nesting several levels for a short SOP. Tables work well for schedules, owners and status, but can be difficult on a phone. Keep tables narrow, label each column and avoid splitting one idea across many merged cells.

Use descriptive link text. "Read the current Google Docs Help article" is clearer than "click here". A link should have a purpose, and the reader should know whether it opens another resource or an internal section. Add a bookmark to a long document when you want to jump to a specific point, such as the escalation section. Check that the link still points to the right heading after revisions.

Page setup, headers, footers and page numbers support longer documents. Use page numbers when the reader may refer to a page during review. A header can identify a document title or version, but should not contain private personal information. Before adding a logo or image, confirm that you have permission to use it and add useful alternative text where available. Decorative images should not distract from the content.

For the SOP, insert a table of contents after the title and purpose. Docs builds it from heading styles, not from text that merely looks like a heading. When the sections change, refresh the table of contents and test each entry. A table of contents is most useful when the document is long enough to need navigation; do not add one to a short note just to decorate it.

### Lesson 3: Collaboration without losing ownership

Sharing a document grants access; it does not transfer responsibility for protecting it. Before sharing, inspect the recipient, role and link scope. Use Viewer when someone only needs to read, Commenter when they need to provide feedback, and Editor only when they should change the document. For a practice review, use Restricted access and invite a test account or mentor who has agreed to review it.

Comments are useful for a question or a focused review note. Quote a short phrase or select the relevant text, explain the issue, and suggest a next step. Avoid comments like "fix this" without saying what is wrong. Use @mentions only when a specific person needs to act and they have access to the file. Comments can expose the discussion to everyone who can see the document.

Suggesting mode proposes edits without silently replacing the owner's text. It is useful when a reviewer wants to show a possible wording change. The document owner can accept or reject each suggestion. Use Suggesting mode for the Week 2 proposal review and record why you accepted or declined a suggestion. The objective is a better document, not accepting every comment.

Version history helps you see or restore earlier versions of a Google file. Name a version before a major review, for example `Before mentor review` or `After comments round`. A named version is a checkpoint, not a backup in another account. If a change causes a problem, inspect the history and restore only the parts you understand. Do not overwrite another person's work without discussing it.

Google Docs includes features such as comparing documents and building blocks, but the menu names and availability can change. If an option is absent, use version history, comments or a clear manual comparison instead. These optional features are not required for the assignment.

> **Privacy:** Do not use a real customer's order or a real employment proposal in a public link. A link can be forwarded. Use only the fictional Fresh Bites content and share it with a restricted practice audience.

### Lesson 4: Templates, voice typing and proofreading

Templates and reusable building blocks can speed up repeat work. A template is a starting point, not proof that the content is correct. Make a clean copy before editing it. Remove placeholder instructions and check the owner, date, headings, links and table of contents before sending the final file.

Voice typing can help draft text when typing is difficult or a first draft is easier to speak. As checked on 12 November 2026, Google's help lists English (Nigeria) among supported voice-typing language and accent options in Docs, and supports current versions of Chrome, Edge and Safari. Browser speech-to-text processing is involved. Check the browser permission, microphone, language choice and privacy rules before use. Do not dictate a real customer's private information into a training document. Proofread punctuation, names and numbers; speech recognition can be wrong.

Use spelling and grammar suggestions as a review aid, not an authority. Check unfamiliar names, Naira amounts, dates and URLs yourself. Read the SOP aloud or ask a reviewer to follow its steps. If a step depends on a decision not stated in the document, add a clear question or escalation path.

### Lesson 5: Export and publish responsibly

Before export, inspect page breaks, table width, headers, links and the table of contents. A PDF preserves layout for reading, while a Word export may be useful when the recipient needs to edit in another suite. Different applications can render fonts, margins and tables differently; reopen the exported file and check it.

Use Drive sharing settings when a team needs a working document. A published web link is different from a restricted collaboration copy. Do not publish a proposal or SOP publicly merely to make it easy to open. If a recipient needs a copy but not edit access, choose the least permission that supports the task. Re-check the link in a controlled second account and remove temporary access after review.

## Common mistakes

- Formatting headings with bold and larger font but leaving them as normal paragraphs.
- Creating a table of contents before applying heading styles, then forgetting to update it.
- Giving Editor access to every reviewer by default.
- Resolving comments without checking whether the suggested action was completed.
- Treating version history as a separate backup.
- Accepting voice typing or spelling suggestions without proofreading the final copy.
- Publishing a live document with a public link because it seems easier than restricted sharing.

## Practice Exercises

1. Apply Title, Heading 1 and Heading 2 styles to the SOP starter and inspect the outline.
2. Add a checklist and a table that lists each order-handling step and its owner.
3. Insert a table of contents, then rename one heading and refresh the table.
4. Add one bookmark and a descriptive link to a relevant section.
5. Share the proposal with a practice reviewer as Commenter, then add a focused comment.
6. Use Suggesting mode for two wording changes; accept one and reject one with a reason.
7. Name a pre-review and post-review version, export to PDF and inspect the final pages.

## Weekly Assignment (Due Before Week 3)

**Submit:**

1. A formatted Standard Operating Procedure for handling WhatsApp orders at Fresh Bites. It must include headings, a table of contents, one checklist table and a clear escalation section.
2. A two-page proposal using the fictional catering brief. Mark date, budget and delivery details as unconfirmed placeholders; do not invent a quotation.
3. Evidence of a comment and suggestion round with a practice reviewer, plus named versions before and after the review.

**Grading guide:** structure and formatting (35%); clarity and completeness (30%); collaboration evidence (25%); final polish (10%).

**Definition of done:**

- [ ] Both files use consistent styles and meaningful headings.
- [ ] The SOP's table of contents opens the correct sections.
- [ ] The proposal distinguishes confirmed details from assumptions.
- [ ] A reviewer could read or comment but only the owner can approve final wording.
- [ ] The exported PDF was inspected and contains no personal or customer data.

## Facilitator Notes

Ask learners to use only fictional files. If a learner cannot access a second account or share externally, accept screenshots of the permission panel plus a written access plan; do not ask them to weaken an organisation policy. Encourage reviewers to comment on clarity rather than rewrite the learner's document. Remind learners that voice-typing behavior and menus are browser-dependent.

## Self-Check Questions

1. Why should a heading style be used instead of only bold text?
2. When is Commenter access more appropriate than Editor access?
3. What is the difference between Suggesting mode and a comment?
4. What should you inspect after exporting a Google Doc to PDF?
