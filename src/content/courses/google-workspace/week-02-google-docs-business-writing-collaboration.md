**Goal:** This week you'll build two documents a real business would actually use - a step-by-step order SOP and a short proposal - and run a review round with a teammate. You build by doing, not by reading about formatting.

## What you'll be able to do

- Structure a document with real heading styles, not just bold text
- Add a table of contents, links, tables and page numbers that update cleanly
- Share for review and use comments and Suggesting mode well
- Name versions, respond to feedback and show what changed
- Export a clean, accessible final copy

## Before you start (about 10 minutes)

- Open the [SOP starter](/downloads/google-workspace/sop-content-whatsapp-orders.md) and the [proposal starter](/downloads/google-workspace/proposal-content-fresh-bites-catering.md) in a practice account.
- Skim the [collaboration etiquette](/downloads/google-workspace/doc-collaboration-etiquette.md) sheet for 3 minutes.
- Warm-up: for each starter, jot the sections it needs before you touch any formatting (an SOP needs purpose, roles, steps, exceptions, escalation; a proposal needs summary, plan, assumptions, timeline, next step).

## Try it 1 - Structure first, styling second

**Why it matters:** headings give the document an outline that readers and screen readers can navigate. Bold text alone does not.

**Do this now:**
1. Open the SOP starter. Add a clear Title and a one-line purpose.
2. Apply **Heading 1** to main sections and **Heading 2** to subsections - use the style, not just a bigger font.
3. Open the outline panel and read only the headings. If they read like a useful summary, you're done. If one says "Other", rename it to say what follows.

**You've got it when:** the outline panel alone tells the whole story of the document.

## Try it 2 - Add lists, a table and a table of contents

**Why it matters:** a reader scans steps and tables far faster than paragraphs, and a live table of contents keeps a long doc navigable.

**Do this now:**
1. Turn the order-handling steps into a numbered list (sequence matters) and add a small table of step, owner and status.
2. Add one descriptive link - "Read the current Google Docs Help article", never "click here".
3. Insert a table of contents after the title. Docs builds it from heading styles.
4. Rename one heading, then refresh the table of contents and test that each entry jumps to the right place.

**You've got it when:** every table-of-contents entry opens the correct section after you refreshed it.

> Quick win: add page numbers, then switch between phone and desktop width to see how your table behaves - keep tables narrow.

## Try it 3 - Run a real review round

**Why it matters:** sharing grants access but not responsibility. Reviewing without overwriting the owner's work is a core workplace skill.

**Do this now:**
1. Share the proposal with a practice reviewer (a test account or mentor) as **Commenter**, using Restricted access.
2. Have the reviewer add one focused comment - quote the phrase, name the issue, suggest a fix. No "fix this".
3. Switch to **Suggesting mode** and make two wording changes. As owner, accept one and reject one, and note why.

**You've got it when:** the doc shows a comment and two suggestions, and only the owner approved the final wording.

## Try it 4 - Name versions and export a clean copy

**Why it matters:** named versions are checkpoints you can return to, and a quick export check catches layout surprises before anyone else sees them.

**Do this now:**
1. In version history, name a version `Before mentor review`, then after changes name one `After comments round`.
2. Try voice typing one sentence (Docs supports English (Nigeria)); proofread the punctuation, names and numbers - speech recognition slips.
3. Export the SOP to PDF, reopen it, and check page breaks, table width, links and the table of contents.

**You've got it when:** you can restore an earlier version on demand, and the exported PDF looks right with no personal data in it.

### Watch out for

- Formatting headings with bold and a bigger font but leaving them as normal paragraphs.
- Building a table of contents before applying heading styles, then forgetting to refresh it.
- Giving Editor access to every reviewer by default.
- Resolving a comment without checking the fix was actually done.
- Treating version history as a separate backup.
- Trusting voice typing or spell-check without proofreading.
- Publishing a live doc with a public link because it felt easier.

> **Privacy:** Never use a real customer order or a real employment proposal in a shared link - links get forwarded. Use only the fictional Fresh Bites content with a restricted audience.

## This week's build: an SOP and a proposal with a review trail

Produce two documents a small business could use tomorrow:

1. A formatted **Standard Operating Procedure** for handling WhatsApp orders at Fresh Bites, with headings, a table of contents, one checklist table and a clear escalation section.
2. A **two-page proposal** from the fictional catering brief. Mark date, budget and delivery as unconfirmed placeholders - do not invent a quotation.
3. Evidence of a comment and suggestion round with a reviewer, plus named versions before and after.

*Tip: hand the SOP to someone and have them follow it step by step. If they get stuck, the SOP needs a line, not the reader.*

### Grading guide

| Criteria | Weight |
|---|---|
| Structure and formatting | 35% |
| Clarity and completeness | 30% |
| Collaboration evidence | 25% |
| Final polish | 10% |

### Definition of done

- [ ] Both files use consistent styles and meaningful headings.
- [ ] The SOP's table of contents opens the correct sections.
- [ ] The proposal separates confirmed details from assumptions.
- [ ] A reviewer could read or comment, but only the owner can approve final wording.
- [ ] The exported PDF was inspected and contains no personal or customer data.

## Extra quick wins (optional)

- Add a bookmark to the escalation section and link to it from the top of the SOP.
- Rewrite one wordy paragraph as a three-item checklist and see how much clearer it reads.
- Export the proposal to Word as well, reopen it, and spot what shifted.

## Mentoring Session Plan (90 minutes)

| Time | Activity |
|---|---|
| 0–10 min | Review Week 1 sharing choices and assignment questions |
| 10–25 min | Demonstrate heading styles and the outline using the SOP starter |
| 25–40 min | Build and refresh a table of contents; check links and page layout |
| 40–60 min | Pair review: add a comment and a suggestion to the proposal |
| 60–75 min | Name versions, compare the review state and export a PDF |
| 75–85 min | Peer check for readability, assumptions and privacy |
| 85–90 min | Confirm assignment evidence and preview Sheets |

## Facilitator Notes

Ask learners to use only fictional files. If a learner cannot access a second account or share externally, accept screenshots of the permission panel plus a written access plan; do not ask them to weaken an organisation policy. Encourage reviewers to comment on clarity rather than rewrite the learner's document. Remind learners that voice-typing behavior and menus are browser-dependent.

## Can you do these now?

1. Why use a heading style instead of only bold text?
2. When is Commenter access more appropriate than Editor access?
3. What is the difference between Suggesting mode and a comment?
4. What should you inspect after exporting a Google Doc to PDF?
