**Goal:** Build a navigable proposal and collaborate on a practice copy without exposing real recipient or client information.

## Learning Objectives

By the end of this week, you can:

- Use the Navigation pane and heading styles to manage a long document.
- Insert and update a table of contents, captions, cross-references, notes and a simple bibliography.
- Apply section breaks, different first-page formatting and page numbering.
- Create a reusable template from a clean document.
- Review changes with Track Changes and comments, compare versions and accept or reject edits deliberately.
- Prepare and preview a mail merge from ten fictional records without sending it.

## Tools / Accounts Needed This Week

Word desktop is recommended for the full set of long-document, mail merge and content-control features. Word for the web may offer a different subset; use the desktop app only if it is legally available to you. You also need the proposal starter, the fictional customer CSV, and a local copy of the Week 2 work. OneDrive is optional; if used, share only with an account you own or an authorised training participant.

## Lessons

### Lesson 1: Navigation pane and heading structure

A long document needs a map. Apply **Heading 1** to each main proposal section and **Heading 2** to subsections. Open the Navigation pane, usually from **View** or by using **Ctrl+F**, and inspect the heading list. You can select a heading to jump to its section and, in some versions, drag headings to rearrange sections. Recheck the content after moving a section so that tables and captions stay with the right text.

Keep the hierarchy meaningful. A heading should name the topic that follows; it should not be used only to make a phrase look large. If you need a small label inside a paragraph, bold text may be better than adding another heading level. A clear structure improves navigation for everyone, including users of screen readers.

### Lesson 2: Table of contents, captions, references and citations

An automatic table of contents is generated from heading styles. Choose the References command, select an automatic table, and update it after changing section titles or page order. A manually typed contents list will not update when the proposal changes.

Use **Insert Caption** for a table or figure. A caption gives the object a number and a short description. Cross-references can point to that caption and update when numbering changes. In a long practice proposal, add a caption such as “Table 1: Fictional service-planning assumptions” and refer to it in the paragraph that discusses the assumptions.

Footnotes add a brief note at the bottom of a page; endnotes collect notes at the end of a document. Use them only when they help the reader. A bibliography or reference list should identify sources actually consulted. Do not invent a source, quote or citation. In this course, the Fresh Bites case values are invented examples, so label them as such rather than presenting them as market research. Citations are introduced conceptually; follow the referencing style required by your school or organisation.

### Lesson 3: Section breaks and page numbering

A **page break** starts a new page but keeps the same section settings. A **section break** divides a document so that one part can use a different orientation, header, footer or numbering style. For the proposal, a section break can separate a cover page from the body, or allow an appendix table to use landscape orientation.

| Break | Starts a new page | Can change headers, orientation or numbering by section |
|---|---:|---:|
| Page break | Yes | No |
| Section break | Depending on break type | Yes |

Insert a section break from the Layout or Breaks command. Turn on formatting marks if you need to see where breaks are. In the new section, inspect whether **Link to Previous** is active for the header or footer. Use **Different First Page** for a clean cover. Insert page numbers using the automatic command and verify the first body page has the intended number. If numbering unexpectedly restarts or continues, check the section's format and previous-section link rather than typing a number manually.

### Lesson 4: Templates

A template is a reusable starting point with styles, page settings and placeholder content. Create one from a clean copy of the proposal structure: title, heading levels, body style, standard table and a footer with a version placeholder. Remove sample customer names and business details before saving it as a reusable template. Use the app's template file type if available, or store a clearly labelled clean copy in a template folder.

When creating a new document from a template, save it under a new name immediately. Otherwise, you may overwrite the template itself. Add only information that belongs in every document; keep client-specific text in the new copy.

### Lesson 5: Track Changes, comments, compare and co-authoring

**Track Changes** records insertions and deletions so a reviewer can see what changed. Turn it on before editing a copy, not after, and check that the correct document is open. Use comments for questions or context rather than placing all discussion in the document body. A mentor can suggest edits; the author remains responsible for accepting or rejecting them.

Use **Compare** to inspect two versions when the edit history is missing. Review differences section by section. Accept or reject changes deliberately; do not choose “Accept All” simply to remove coloured marks. After review, turn Track Changes off and confirm the final version is clean.

Co-authoring can allow more than one authorised person to edit a supported cloud file at once. Agree on a reviewer, scope and deadline. Avoid making simultaneous changes to the same paragraph during training. Use a copy with fictional content and remove temporary sharing access when the exercise ends. If a cloud account or feature is unavailable, simulate review by saving `v01` and `v02` copies and using Compare.

### Lesson 6: Mail merge with a fictional Excel or CSV list

Mail merge combines a document template with rows from a recipient list. In Word desktop, use the Mailings tab to start a letter merge, select the supplied CSV, insert fields such as FirstName and PreferredPackage, preview each record, and finish by creating a new merged document for review. Labels use the same recipient source but a label layout.

Before connecting a real list, check the headers, blank cells, duplicates, spelling, and whether every recipient is authorised to receive the message. A CSV is plain text; do not assume it protects private information. For this class, use only `customers-list-10.csv`. Its `.invalid` addresses are intentionally non-deliverable examples. Do not send the merged letters or labels. Review all ten results in Word, confirm fields appear correctly, and close without sending.

Mail merge can repeat a wrong name or offer ten times. Preview every record and check punctuation when a field is empty. Keep the recipient list in a restricted folder and delete practice copies when no longer needed.

> **Warning:** Preview the merged result but do not send this practice campaign. The sample addresses use the reserved `.invalid` domain and are not real recipients.

### Lesson 7: Simple fillable forms with content controls

Content controls can create a basic form with a text field, date picker, check box or drop-down where supported. Add a short instruction beside each field, use clear labels, and make the tab order logical. Protecting a form can prevent accidental changes to its layout, but it does not encrypt the file or control who can open it.

Use fictional entries for practice. Do not collect sensitive information in a class form. For a real form, ask the organisation what information is necessary, how it is stored, who can access it and how long it is retained. If the feature is missing in your version, provide a plain editable table with labelled blank cells instead.

### Lesson 8: Accessibility checker and alt text

Run the app's accessibility checker where available, then review each suggestion. Use descriptive heading styles, meaningful link text, sufficient contrast, simple tables with header rows, and alt text for informative images. Do not convey meaning only through colour. A checker is an aid; it cannot decide whether a heading is understandable or whether an image description is useful.

For the proposal's table, identify the header row and avoid splitting information across merged cells. For a decorative shape, mark it decorative if the app supports that option. Read the document from top to bottom and use the Navigation pane to test its structure. If a shared document contains comments or tracked changes, ensure the final accessible copy does not expose private reviewer notes.

### Lesson 9: Protecting and sharing documents safely

Before sharing, save a review copy, check the filename and recipient, and choose the least permission needed. A view-only link may still allow downloads depending on account policy; inspect the sharing panel rather than assuming. Do not use a public link for private work. When sharing to a training partner, use an account and content authorised for the exercise and remove access afterwards.

Document properties and metadata may include author names, comments, tracked changes or hidden text. A document inspector or **Check for Issues** feature can help identify some of these items in desktop Word. Review its findings before removing anything; metadata removal can also remove useful information. Keep a clean practice copy and do not upload private client material to a third-party conversion service.

## Common Mistakes

- Typing a contents list manually and forgetting to update it.
- Using page breaks where section-specific headers or numbering require a section break.
- Accepting every tracked change without reviewing the meaning.
- Merging a real customer list without permission or sending practice messages.
- Assuming a protected form is encrypted or secure.
- Sharing a file with a broad link when a named, view-only link is enough.
- Treating an accessibility checker as a substitute for a human review.

## Weekly Assignment (Due Before Week 4)

Submit an **eight-page-or-longer business proposal** for the fictional catering contract, based on `proposal-content.md`. It must have a generated table of contents, heading structure, at least one captioned table, page numbers, and a section break. Submit a **mail merge** of the promotional letter to the ten fictional customer records as a review document; do not send it. Complete one Track Changes round with the mentor on a practice copy and include the reviewed copy or a screenshot of the review state.

**Grading guide:** structure and navigation 30%, mail merge 25%, collaboration use 20%, polish 25%.

**Definition of done**

- [ ] The proposal has eight or more pages and a working, updated table of contents.
- [ ] Headings, page numbers, section break and table caption are present and readable.
- [ ] All sample amounts and assumptions remain labelled as fictional.
- [ ] Ten merge records preview correctly; no practice letter is sent.
- [ ] One review round shows tracked edits or a documented Compare result.
- [ ] The final copy has been checked for accessibility, sharing permissions and private metadata.

## Facilitator Notes

Prepare the checkpoint from fictional text only. Confirm that learners are in a review copy before editing. Do not collect or display actual customer lists, account identifiers or email addresses. If the learner's version lacks a feature, accept a demonstrated equivalent and note the limitation rather than requiring a purchase. During the track-changes round, ask the author to explain a decision; do not silently rewrite the learner's work. Allow the full 90-minute checkpoint in a quiet setting with accessible instructions.
